# 专辑排序与审核

这是唱片目录中各张专辑的顺序，与单张专辑内部的“版本排序”分开保存。

- 专辑管理右上角“调整专辑顺序”进入 `/contributor/albums/order`。新增/编辑专辑的同名入口另开标签页，保留当前未保存表单。
- 默认按已批准的首次发行日期从早到晚，未填时使用最早有效版本日期，未知日期最后。
- 只有已发布专辑进入排序清单；新专辑完成内容审核后才加入。上移/下移自动选择手动排序，也可恢复按日期。
- 排序和可选理由提交为独立申请，管理员自己的申请也必须审核。待审时不改变公开目录，刷新仍可看到申请。
- 管理员后台“专辑排序”逐条显示提交人、理由（空值为“无”）、修改前后模式与完整名称/日期顺序，可批准或拒绝。
- 手动排序中的新发布专辑追加在已排项目后，新增项目之间依发行日期排列。不重排专辑内部版本，也不改变封面选择。

## 数据与权限

`catalog_order` 仅保存已批准的全局模式、稳定专辑 ID 序列和修订号；`catalog_order_requests` 保存不可变前后快照及审核结果。追加两个表，不改写任何已有专辑、版本、用户或媒体记录。公开读取遇到尚未建表的数据库时只采用日期排序，不创建表。

`/api/contributor/catalog-order` 要求真实、获批、未停用的服务端会话，POST 继续执行同源保护。普通成员只能查看自己的申请，管理员可查看全部。只能提交当前已发布 ID 的完整排列，不能通过排序隐藏、删除、引入草稿或修改专辑内容。每人最多一条待审申请；无直接发布入口。

提交/批准均核对全局修订号与已发布专辑 ID/修订号指纹。等待期间发生发布、删除、内容批准或其他排序批准，旧申请须拒绝后重新提交，避免覆盖新目录。审核、设置和审计记录在同一事务内完成。

## 本地验证

所有写入测试使用临时隔离 SQLite，不使用生产数据库、真实账号或 COS 上传。

1. 普通成员登录，专辑管理进入“调整专辑顺序”，确认初始日期排序。
2. 将第二张上移，提交理由；刷新后待审申请仍存在，公开目录顺序保持。
3. 管理员后台进入“专辑排序”，展开查看前后差异和理由，批准后公开目录更新。
4. 将模式恢复按日期，提交并批准，确认恢复时间排序。
5. 验证 360、390、430、768、1440px 无横向溢出，新建专辑入口及原版本排序仍可用。
6. `npm run typecheck`、`npm test`、`npm run build`；`tests/catalog-order.test.ts` 覆盖审核/持久化/权限/非法 ID/并发/事务回滚及不改专辑快照。

部署先备份 SQLite，仅追加空表；重启既有 systemd 服务。部署验证不登录、不提交生产申请，逐表比较备份以确保既有记录不变，不改 COS 或网络配置。
